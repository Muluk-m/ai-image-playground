# 系统质量与真实使用走查（2026-11-13）

承接两份 11 月的体检：[架构、数据库与性能走查](architecture-performance-audit-2026-11.md)和[仓库审查清单](../audit/2026-11-repo-audit.md)。那两份看的是设计与代码；这一份看两件它们没看的事：bug 是从哪里漏出去的，以及用户实际在用什么。

本仓库公开，所以这里只写比例和工程指标，不写用户身份和账号规模。

## 结论

后端的核心设计没有问题，不建议重写。「质量差」的感受来自三件事：

1. 工程投入和真实使用错位：用户几乎只用工作台，修复和新功能却集中在画布与智能体对话。
2. 前端状态太复杂：同一份媒体同时活在多处，交接处反复出错。
3. 发版太频繁，过半落在用户的工作时间。

## 数据来源与口径

- 提交与 CI：`main` 自 2026-10-14 起的 30 天，`git log` 与 GitHub Actions。
- 使用数据：生产 Admin 的只读接口（概览、任务列表、前端错误），同一 30 天窗口。只用 GET，拉到本地的明细分析后已删除。
- 题材分类按提示词关键词粗分，只能看量级。
- 入口口径来自 Admin 的任务来源：`manual`（没有会话的任务）、`chat`（挂在会话上，含画布里由智能体触发的生成）、`cli`。画布节点上手动点出的图可能计入 `manual`，画布的实际用量拆不准。

## 用户实际在怎么用

- **使用高度集中。** 一个团队客户的两个账号贡献了近八成任务，其余多为内部测试账号。
- **入口是工作台。** 该团队约 88% 的任务来自工作台手动出图，约 12% 来自对话或画布。对话来源的任务里，内部测试占了大半。
- **做的是改图。** 约 58% 的提示词是参考图改图（换字、换色、换背景、保留版式），约 22% 涉及文字、排版或海报。提示词中位数 228 字，P90 约 500 字。
- **靠重抽挑图。** 约 29% 的任务是同一提示词的重复提交。
- **模型集中。** `gpt-image-2.5-flare` 约 64%，`gemini-nano-banana-2.1` 约 31%，两者合计约 95%。视频任务占比不到 0.5%，失败率约四分之一。
- **等待偏长。** 主力模型从提交到完成 P50 53 秒、P90 162 秒；`gemini-nano-banana-2.1` P50 42 秒、P90 136 秒。
- **失败原因。** 任务成功率 97.7%。失败里约一半是内容审核拦截，且集中在单个账号；约四成是上游报错。
- **时段。** 工作日 9–17 点为主，22–23 点有一个小高峰。

## 系统质量

### 1. bug 带着全绿的测试进了生产

30 天内 `main` 有 659 个提交，修复类约 307 个，功能类约 93 个，约 3.3 比 1。同期 `main` 上的 Web checks 200 次里 197 次成功，测试代码约 24 万行，与源码（约 26 万行）相当。

所以问题不是测试少，也不是 CI 不稳。漏出去的 bug 多数属于刷新恢复、多标签页、本地与云端同步、时序竞争，单元测试覆盖不到这些。

修复按主题粗分（标题关键词，有重叠）：

| 主题 | 修复数 |
| --- | ---: |
| 画布、节点 | 66 |
| 智能体对话、轮 | 49 |
| 部署、发布、Pages、CI | 30 |
| 轮询、重试、超时、卡住 | 23 |
| 刷新、缓存、恢复 | 20 |
| 上传、附件、参考图 | 13 |
| 登录、会话 | 12 |
| 批量 | 12 |

### 2. 画布的媒体状态有多个来源

画布是修复最集中的地方。同一张图会同时存在于本地 IndexedDB、上传租约、云端媒体、画布节点、作品库候选和其他标签页。修复标题几乎覆盖了每一对之间的交接：换云地址时闪「素材缺失」、上传与提升抢同一张图、永久「上传中」的节点、旧坏节点阻塞保存、别的标签页改名后本页不更新。

### 3. 三个巨型文件就是修复最多的文件

| 文件 | 行数 | 30 天内出现在修复提交里的次数 |
| --- | ---: | ---: |
| `apps/web/src/features/canvas/components/NodeCanvas.tsx` | 3172 | 32 |
| `apps/web/src/store.ts` | 3258 | 9 |
| `apps/web/src/features/agent/store.ts` | 2898 | 9 |

`AgentToolCard.tsx`（1484 行，15 次）、`AgentComposer.tsx`（1662 行，14 次）、`InputBar.tsx`（1878 行，11 次）紧随其后。

### 4. 发版频率与用户时段重叠

30 天内生产部署 workflow 成功 270 次，分布在 20 天里，日均 9 次，其中 54% 落在北京时间 9–18 点。其中一部分运行按设计跳过了实际发布，真实滚动次数低于这个数，但量级不变。

前端错误里最多的两类正是发版的副作用：启动失败（`BootFailure: resource` / `preload`，7 天内 4 台设备）和旧页面加载分片失败（`Failed to fetch dynamically imported module`）。#1532、#1813、#1814 已经分别做了自动刷新和保留旧版文件，错误仍在出现，需要查清剩下的路径。后端每次发版还要排空在跑的任务。

### 5. 上游拖慢体验

- 主力模型 P90 接近 3 分钟。
- `gemini-3.1-flash-lite-image` 平均每个任务调用上游 4.3 次（55 个任务、237 次调用）。
- 内容审核拦截占失败的一半，用户侧只看到失败，不知道原因和怎么改。

### 6. 运维遗留

- `image-playground-internal` 已在 #1706 退役，但服务器上仍有一整套容器在运行，最后一次发布在 2026-10-31。
- `apps/web/src/__tests__/scripts/deployLock.test.ts` 的「永远只有一个抢到」不稳定，2026-11-13 在 overlay 的 main 检查里失败过一次，重跑通过，期间挡住了 `private.lock` 的更新。

### 没有问题的部分

两份 11 月体检都认为后端核心设计合理：任务行持久化、租约加 fence、事务内预扣、上游任务 ID 落库后只轮询不重提。这次的失败分布和修复热点也没有指向它。

## 建议

按投入产出排序。追踪 issue 见 [#1844](https://github.com/Muluk-m/ai-image-playground/issues/1844)。

### 系统质量

1. **发布改成按窗口批量发**（#1845）。例如中午、傍晚、夜间各一次，紧急修复走单独通道。成本最低，直接减少用户在使用中遇到的启动失败和任务排空。
2. **查清发版后旧页面仍会启动失败的路径**（#1846）。
3. **给工作台建端到端主路径测试，作为发布门禁**（#1847）。参考图改图、同提示词重抽、刷新后任务恢复、作品库、登录态续期。之后的 bug 修复带上能复现问题的用例。
4. **前端状态拆分与画布媒体单一来源**（#1848）。`store.ts` 按领域拆，借状态机迁移一起做；画布节点只存媒体身份，状态从一处推导。画布使用率低，放第二梯队。
5. **清理遗留**：下线 internal 容器（#1849，需 Nain 批准），修 `deployLock` 的不稳定测试（#1850）。

### 产品

1. **重抽与多张对比**（#1851）。29% 的重复提交说明用户在靠重抽挑图。
2. **参考图改图做成一等流程**（#1852）。换字、换色、换背景、保留版式给快捷入口，并评估中文文字的出图准确率。
3. **团队模板与品牌预设**（#1853）。提示词长、重复使用多，适合沉淀成品牌色、字体、版式模板。
4. **等待与失败的体验**（#1854）。预计完成时间、完成提醒；内容审核拦截时说明原因并提供改写重试。
5. **画布与智能体先只修 bug、暂停加功能，并做用户访谈**（#1855）。是否继续投入，取决于主要用户为什么不用它们。

## 局限

- 使用数据只有 30 天，且集中在一个团队，不代表更广的用户群。
- 修复数按提交标题统计，一个提交可能修多处，也可能只是文案；它反映的是精力去向，不是缺陷密度。
- 发版与前端启动失败之间是时间上的吻合加错误类型的吻合，没有逐条对上发布时间。#1846 负责验证。
