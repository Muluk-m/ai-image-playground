# 人工扫码收款：套餐续费最小闭环

状态：2026-10-01 评审修订。C 端沿用弹框已确定；本文是实现约束，订单功能尚未上线。原型中充值、通知重试、统计等演示不等于首期范围。

## 首期范围

只做已有套餐用户的同档、同权益版本续费，支持现有单月、三个月和年度周期，按周期一次付款、不自动续费，套餐积分仍按月发放。无套餐首购、充值、跨档升级及跨权益版本续费不进入首期自助支付。充值比例未确定，不以邀请返利折算率替代。

最小链路：选择续费周期 → 服务端创建锁价订单 → 支付弹框显示收款码和短订单码 → 我已付款 → Admin 待核款列表 → 对照真实收款后确认或拒绝 → 同事务续期、记账和返利 → 用户看到完成。

Admin 只需要待付款与待核款列表、短码/订单号查找、收款记录反查、订单详情和核款动作。保留免费的积分补偿、赠送套餐、到期日纠正，均要求原因与审计，不记收入、不返利。旧的有偿充值/开通不得继续绕过订单；首期未支持的商品停止新增有偿操作，历史未知结果请求仍可恢复。

后期：充值商品、首购、跨档/跨权益版本升级、通用 outbox 与自动重试、申报版本、订单内凭证上传、全量筛选与经营统计、完整现金退款及返利冲正。

## 约束

### 对账：短订单码，保持整数售价

采用短订单码方案，不采用金额尾差，以保留用户明确要求的整数价格。服务端生成 6 位无歧义大写字母数字码，数据库唯一约束、冲突重生成，历史码不复用；短码只是查找键，不能作为查看订单的授权凭据。

支付弹框在收款码上方醒目展示准确整数金额和「转账备注填写 ABC234」，提供复制按钮。点击我已付款时再次提示核对备注；备注缺失时引导通过旁边的客服入口提供付款凭证及订单码，不强制上传。用户自报付款不代表已到账。

Admin 提供「从收款记录找订单」：输入备注短码可直接定位；没有备注时，输入金额与大致付款时间查找候选，列表展示订单号、用户、金额、申报时间供人工核对。候选结果不是自动匹配，不能仅凭金额相等、时间接近或用户截图直接确认。

核款人必须在实际微信/支付宝收款记录中核验，并登记支付渠道、收款码版本、真实交易号、实收金额、到账时间及必要核对备注。支付渠道 + 收款账户标识 + 交易号唯一，一笔实际到账只能履约一张订单；同一交易号重复提交显示原关联订单。收款码版本与收款账户分别标识，换码不应绕过交易去重。

漏填备注、同额多人付款或凭证无法区分时，订单继续待核款并记录未匹配原因；运营联系用户取得交易号等信息，再与收款端核对。无法唯一匹配不发权益。初期不自动导入支付流水，不建独立流水池：运营从支付工具查看真实记录后在 Admin 反查。不得把未知归属款项硬挂给候选用户。

### 状态表

| 状态 | 触发者/条件 | 可转入 | 用户呈现 |
| --- | --- | --- | --- |
| pending（待付款） | 用户创建，服务端锁价并通知运营 | review、completed（管理员核实到账）、cancelled、expired | 金额、二维码、短码、剩余支付时间 |
| review（待核款） | 用户申报，或管理员受理迟到付款 | completed、rejected | 已提交，等待人工核验；无倒计时，勿重复付款 |
| completed（已完成） | 管理员核实真实到账，事务成功 | 无 | 到账与续期结果 |
| rejected（核款未通过） | 管理员确认申报不匹配，必填原因 | review（管理员重开原单） | 原因与联系客服，不引导重新付款 |
| cancelled（已取消） | 用户在 pending 取消 | review（管理员受理已实际付款） | 已取消，已付款请联系客服 |
| expired（已过期） | 服务端判定 pending 超过 30 分钟 | review（管理员受理已实际付款） | 请勿继续付款，已付款请联系客服 |

内部核款备注只在 Admin 展示；拒绝时另填告知用户的原因。

「未匹配」是 review 的核款备注，不另建异常状态或申报版本。拒绝不能代表已退钱；管理员重开必须说明理由、保留历史，仍使用原订单和履约 ID。用户重复申报 review 幂等返回，不能触发重复发放。订单创建成功后即向运营通知一次；用户申报、管理员确认、拒绝和重开均不再发群通知。运营核实真实到账后，可直接确认 pending 订单，无需等待用户申报。completed 不可直接取消/删除。

30 分钟仅是付款窗口，人工核款可晚于窗口。活动在窗口内结束，仍按订单锁定金额履约。核款确认有效期内实际付款但申报晚的，按原价快照处理；超时后实际转账需人工受理、记录原因，确认接受原交易后按原快照履约，无法接受的记录线下处理结果，不能静默丢弃。首期不允许用户自动重开过期或被拒订单。

### 锁价、权益与事务

- 客户端仅提交周期、商品标识和幂等键；服务端校验账户与续费资格，保存整数分金额、商品名称、周期、plan 版本 ID、收款码版本。用户只能读取自己的订单。
- 订单用固定 UUID 履约；`reason` 确定性生成为 `order:<完整订单号>`。请求 hash 中的金额、plan ID、周期、starts_at 和 reason 必须稳定；实际处理时间、核款人备注不能混入该 hash。需首次确定的履约输入在订单锁内固定，不能每次重试使用 Date.now()。
- 核款在一个事务内锁订单及账户，完成真实收款、订阅续期、邀请返利、积分流水、审计与订单完成；不能先调用自行开事务的 grantSubscription/adjustRechargeCredits，再单独更新订单。
- 金额不符、交易号已用于其他订单或套餐资格变化，拒绝履约并保留核款线索。重试、多管理员竞争只能发放一次；账户/邀请人锁序保持一致。
- 现有 `billing_plans` 的权益行改为不可变版本；月度额度和并发不再原地修改，新权益新建版本 ID。订单及订阅指向该 ID，尽量保持 reconcileAccount 和并发门禁的读取路径。
- 现有 planPrices 与权益分表：首期价格仍由订单保存不可变快照，改价仅影响新订单；不为单纯改价创建新权益版本。否则现有同档续费的 plan_id 相等检查会把普通调价变成跨版本迁移。完整商品版本体系放后期。
- 旧订阅保留当前 plan ID，不追溯修改权益。首期续费只能相同版本，旧版本停卖阻止新订单，不得阻止有效锁价订单核款。若需要从旧权益版本续到新版本，须后续设计生效区间，不能覆盖仍在生效的订阅 plan_id。
- 免费补偿/赠送不创建实付、不触发付款返利；生成失败退积分并非现金退款。首期线下退款只留处置记录，不声称系统已自动退款或冲正。

### 一次通知与可信操作人

- 继续使用现有飞书运维告警群。卡片只含订单号、新的付款请求提示与 Admin 链接，不含邮箱、用户名或付款凭证。
- 不在 API 进程同步发 webhook：OPS_ALERT_WEBHOOK_URL 在 worker/host-collector，投递通过 worker 独立维护 hook（API 的账户扫描不消费通知）。首期直接在订单行保存通知状态，不增加通用 outbox 表或重试调度。
- 创建订单事务写入通知 pending；worker 原子抢占一次，发送后写 sent 或 failed，Admin 标红失败。缺配置也算失败；进程在抢占后崩溃或网络结果不明显示 unknown，不自动重发。待付款与待核款订单列表是事实来源，群通知仅辅助；无论通知结果如何都不丢订单、不影响人工核款。
- 可信操作人修复独立交付：Admin 从验证后的 session 注入内部身份，BFF 内部鉴权后使用，不信任浏览器伪造头或 body。保留旧服务/overlay 升级期兼容，并明确旧调用身份来源；不能宣称固定 admin 已能区分共享账号背后的自然人。

### 收款码与历史兼容

个人收款码属于过渡方案，长期经营性使用存在渠道限制收款的可能。收款码失效时 Admin 暂停新下单/支付展示、配置并验证新码，再恢复；受影响的待付款订单暂停展示旧码，不能静默替换历史码。恢复支付记录新展示版本，订单保留旧版本、切换时间与收款账户用于核对；已申报订单照原记录核款。

历史实付不伪造新订单、不补发权益/返利。Admin localStorage 中 `billing.pending-payment:${userId}` 是结果未知的旧付款请求，应按原 operation ID 查询或幂等恢复；关闭旧有偿新请求时仍须保留此恢复通道。旧接口不能作为新订单上线后的绕过路径。
