# 运营覆盖无效时退回基线配置，而不是拒绝启动

运营者在后台设置的运营覆盖存在部署自己的数据库里，优先于随部署下发的基线配置。读到无效的覆盖时，处理分两种：不认识的键直接忽略；认识但取值非法、或会让整份配置通不过校验的，丢弃这一条，改用基线配置，同时记错误日志、发告警，并在后台标红。服务照常启动和运行。

这与 [ADR 0001](0001-capability-config-fails-closed.md)（配置文件损坏即拒绝启动）方向相反，是有意为之。ADR 0001 防的是「配置一坏，就悄悄退到代码默认值」：那会改变经营站的访问边界和功能集合。覆盖层退回的是运营者在基线配置里定好的取值，不是代码默认值，部署的访问边界不会因此悄悄改变。反过来，如果一条坏的覆盖就让整站起不来，后果比 ADR 0001 防的那种情况更糟：回滚到较早版本时，较新版本写入的覆盖键在旧代码里不认识，按拒绝启动的规则就必然起不来。

## Considered Options

- **任何非法覆盖都拒绝启动**（沿用 ADR 0001）。一条手工改坏的记录，或一次正常回滚，就能让整站不可用；而能写这张表的只有后台，后台写入前已经校验过。
- **非法覆盖退回代码默认值。** 这正是 ADR 0001 要避免的 fail-open：退到的不是运营者为这个部署定的取值。
- **丢弃这一条、退回基线配置。** 采纳。

## Consequences

覆盖只能经由 BFF 写入，写入前整份预演推导和校验，不通过就拒绝保存，所以正常情况下不会出现无效覆盖；退回基线只是兜底，并且一定伴随告警。

整份预演与启动校验共用能力的运行时前置条件。例如打开 `accounts:email-verification` 前，必须具备有效的 `RESEND_API_KEY`、`EMAIL_FROM` 和至少 32 字符的 `EMAIL_CODE_SECRET`；不满足时拒绝写入，不改变有效配置、修订号或审计记录。读取已有覆盖也执行同一校验：不满足的覆盖退回基线并告警，其他有效覆盖继续生效。基线自身缺少必需的运行时配置仍按原有启动规则报错，不归入覆盖兜底。

启动期能力（加载计费模块、跑私有迁移、决定启动哪些后台任务的那几项）不接受覆盖，只能通过基线配置加发布改变，不在本 ADR 的退回范围内。
Admin 入口统一为 `/platform-settings`： 「生成模型」页签管理模型上下架，「能力与配额」页签管理运营覆盖。旧 `/models` 与 `/operator-settings` 深链保留并分别重定向；Provider、运行时密钥与直连预算仍属于 `/providers`，不与平台能力覆盖混合。
灵感库的条目、分类与技能目录继续共用 `/inspirations` 运营内容域；侧栏只保留「灵感库」入口，三个页面内部用页签互相切换。技能正文仍随 BFF 镜像发布，分类与条目仍通过原有接口写入。
