# 宿主机采样用只挂只读文件的容器，不挂 Docker socket；宿主机告警由采集方直发

运维看板要看到宿主机的磁盘与内存，而后台容器从里面看不到这些。我们决定在每套部署里加一个很小的采集容器：只从宿主机拿两个只读文件来读磁盘与内存（`/proc/meminfo`，以及待测文件系统上的任意一个文件：对挂进来的文件做 statfs，得到的就是它背后那块盘的用量），不挂整个根目录，用内部令牌把读数交给 BFF 存成宿主机采样，越过阈值时由它自己直接把告警推到飞书，不经过 BFF 和数据库。另外两条路都被放弃了。挂 Docker socket 能多看到容器状态和镜像占用，但 socket 等于宿主机的 root，而 BFF 与 Admin 都经隧道暴露在公网，这个安全面不值得；镜像堆积这个根因已经由部署脚本的保留策略（#497）治掉，磁盘总量加近几天的曲线足够发现「又在涨」。宿主机上的 cron 脚本什么都能看，但 BFF 在宿主机上没有可达的端口，脚本只能绕 `docker exec` 才能交数据，还要在 compose 之外单独安装和维护。

告警由采集方直发是刻意的：磁盘真满的时候，PostgreSQL 和 BFF 多半已经写不动了，一条要靠它们才能发出的「磁盘满了」等于没有。代价是它仍然依赖 Docker 本身活着，以及应用层的三条规则（队列、备份、心跳）由 worker 的维护循环判断，两处各有一份发送逻辑。同一台宿主机上的多套部署会各跑一个采集容器、读到同一份数字；宿主机告警只由其中一套发（其余的关掉 `OPS_HOST_ALERTS`），不做跨部署的去重；每套部署自己的应用告警不受这个开关影响。

## 2026-09-18 补充：CPU、负载与每个容器的资源

那次整机卡死九个小时之后，看板需要回答「是谁吃掉了内存」和「机器是不是重启过」。采集容器因此多挂了几样只读的东西，仍然不挂 Docker socket：宿主机的 `/proc/stat` 与 `/proc/loadavg`（CPU 使用率、核数、负载、开机时间），整个 `/sys/fs/cgroup`（按容器读内存、CPU 累计时间和 OOM 次数），以及部署脚本写下的一张「容器 ID → 容器名」对照表。cgroup 目录只暴露资源计数，看不到容器里的文件、环境变量或进程参数，也不能对容器做任何操作，和 socket 不是一个量级的权限；代价是 cgroup 只认 ID，容器名得靠部署脚本在每次 `up` 之后把 `docker ps` 的结果原地重写进对照表，部署之外重建的容器在下一次部署前只显示 ID。

后台同时只读挂载宿主机上的部署日志，用来列出最近的部署；日志里只有提交号、镜像名和部署账号。
