# CLI 换令牌可重复交付

## 问题

CLI 的刷新与设备码兑换都在事务里立即作废旧凭据，新令牌只通过 HTTP 响应交付。响应在网络上丢失，或 CLI 拿到响应却没写进凭据文件，旧实现下：刷新再拿旧令牌重试被当成令牌被复制，整条连接被吊销；设备码已标记为用过，只能重新授权。

## 决定

沿用 [ADR 0030](0030-idempotent-web-session-refresh.md) 的确定性继任。CLI 在换令牌前，在凭据锁内持久保存一个随机 UUID 请求标识，以 OAuth 扩展参数 `request_id` 随 `/v1/oauth/token` 发送；成功保存新令牌后清除。格式不对返回 `invalid_request`。

- 继任刷新令牌为 `r1.<请求标识的SHA256>.<HMAC>`：HMAC 以前驱凭据为密钥（刷新时是旧刷新令牌，兑换时是设备码），输入包含版本、domain、所属记录 ID（连接 ID 或设备授权 ID）与请求标识。继任 access 由继任刷新令牌以独立 domain 的 HMAC 导出。数据库仍只存哈希。
- 退休刷新令牌记录新增可空的 `request_key_hash` 列与 `(connection_id, request_key_hash)` 唯一索引（迁移 0095）。旧后端写入 NULL 仍兼容。
- 当前令牌与新标识：正常轮换，退休行记下标识哈希。当前令牌与本连接已完成过的标识：返回 `refresh_request_completed`，当前令牌仍有效，CLI 换新标识重试。
- 已退休令牌带标识：推导继任；与连接当前的刷新与 access 哈希一致、连接未吊销未过期时，按库里的到期时间重发同一组令牌；否则 `invalid_grant`，不吊销连接。
- 已退休令牌证明不了（不带标识，或标识推导不出当前令牌）：退休行无标识时，作废它的轮换不是新 CLI 做的（新 CLI 的重试总带标识），按 OAuth 2.1 §4.3.1 视为被复制、吊销整条连接；退休行有标识时只拒绝，写 `cli.token.retired_rejected` 审计与日志，持有旧令牌的一方不能借此踢掉健康连接。
- 重发时 access 已过期（`expires_in` 为 0）：CLI 保存后立即换新标识再轮换一次，与 ADR 0030 的两步恢复一致。
- 设备码兑换带标识：首次兑换用推导出的令牌建连接；已兑换的设备码在到期后一小时内带同一标识重试时，按同样规则重发，不同标识、不带标识或超过窗口按已用拒绝。连接已经刷新过就不再重发兑换时那一组。

## 取舍

设备授权表不加列：继任令牌由设备码、设备授权 ID 与标识推导，按推导出的哈希查连接即可判断是否同一次兑换。并发同标识刷新由连接行的 `FOR UPDATE` 串行化，后到的请求走退休令牌分支重发同一结果；该分支不锁退休行、只锁连接行，与轮换事务的加锁顺序一致。

## 发布

先发布支持 `request_id` 的后端，再发布带持久标识的 CLI（#1730、#1731）。新 CLI 发布后若把后端回滚到不认 `request_id` 的版本，旧后端静默忽略该字段，恰好处在丢响应重试中的连接会被当成重放吊销，用户需重新授权；回滚前须知悉。旧 CLI 不传标识，行为不变。0095 只加可空列与索引，新旧两代后端都可运行；回滚先部署不读该列的版本，再执行 `rollback/0095_cli_refresh_request_identity.down.sql`。
