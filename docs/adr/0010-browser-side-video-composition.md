# ADR 0010：时间线成片在浏览器里合成

状态：已接受（2026-09-18）。关联：#571（D7、D8）、#573（技术验证）、#579（实现）。

## 背景

时间线要能导出一条成片。服务端 ffmpeg 拼接（#554）已被否决：生产机 3.6 GB 内存，重编码是 CPU 与内存的尖峰，会和线上服务抢资源。片段本来就要下载到浏览器预览，合成也可以在用户机器上做。

## 决定

- 用 WebCodecs 在浏览器里解码、合成、编码，容器读写用 [`mediabunny`](https://github.com/Vanilagy/mediabunny)。它的许可证是 **MPL-2.0**：文件级 copyleft，原样依赖不影响本仓库；修改它的源文件须公开这些文件。
- 成片规格：
  - 分辨率跟第一段，30 fps 固定帧率；
  - 比例不同的段等比缩放、居中加黑边；
  - 音频统一成 48 kHz 双声道（`decodeAudioData` 重采样），没有音轨的段补静音；
  - H.264 + AAC 的 mp4。
- **视频编码固定使用 `latencyMode: 'realtime'`**。Safari 在默认（`quality`）模式下，编码器编到第 5～8 帧后不再产出，`CanvasSource.add` 一直等背压释放，永不返回；实时模式下 Safari 与 Chrome 都完整通过。代价是 Safari 实时模式码率偏低（见下表），这次先接受。
- 输出时间轴按输出帧号计时，不用源帧时间戳：源帧率低于 30 时同一源帧会被取多次，用源时间戳会产生重复 DTS。
- 上限：64 段、总长 600 秒（2026-10-13，#1153）；段数使用时间线同一常量。逐段下载和解码，Worker 通过带背压的 `StreamTarget` 按最多 1 MiB 分块写入 OPFS；主线程不再同时保留全部解码音轨，输出也不累计为一个 `ArrayBuffer`。
- OPFS 文件关闭后交给下载；保留一天供排队下载使用，下次导出清理过期文件。失败/取消时终止 Worker，等在途解码与写盘结束后清理残件。
- 浏览器缺少 H.264/AAC 编码或 OPFS 写入能力时，禁用「导出成片」，提供「下载全部片段」（zip）作为回退。ZIP 逐段分块打包；无 OPFS 时保留 Blob 回退。现有 ZIP 写端不支持 ZIP64，达到 4 GiB 前明确报错并清理，提示分批下载。

## 实测（macOS，本地静态页，测试片由 ffmpeg 生成）

测试片覆盖 16:9 / 9:16 / 1:1、24 / 25 / 30 fps、44.1 kHz / 48 kHz / 无音轨。

| 浏览器 | 编码模式 | 4 段混合，29 秒 | 8 段 1080p，64 秒 |
| --- | --- | --- | --- |
| Chrome 152 | 默认 | 5.7 秒，8.3 MB，JS 堆约 100 MB | 11 秒，52 MB，JS 堆约 140 MB |
| Chrome 152 | realtime | 6.9 秒，8.3 MB | 11 秒，52 MB |
| Safari 27 | 默认 | 第 1 段第 5 帧后卡死 | 未能开始 |
| Safari 27 | realtime | 6.6 秒，3.3 MB | 18.3 秒，25.7 MB |

所有成片 `ffmpeg -f null` 完整解码零告警。抽帧确认竖屏和方形段都是等比居中、两侧黑边；无音轨段实测 -91 dB 静音，其余段有声。Safari 不提供 `performance.memory`，没有堆内存数字。

## 未验证与风险

- Firefox：测试机未安装，未测。它的 H.264 编码依赖系统能力；探测为假时走回退。
- iOS Safari、低端设备：未测。长时间编码可能被后台挂起，所以导出期间页面需在前台。
- Safari 默认模式卡死的根因没有定位（可能是 WebKit 或 mediabunny 的问题）。升级 mediabunny 或 Safari 后应重测，能用默认模式时改回，以换取更高画质。
- 真实上游片段：测试片是本地生成的 H.264，和上游产物同一编码族；上线前用线上视频再做一次端到端验证（#579 的验收）。

## 64 段扩容实测（2026-10-13，#1153，仅 dev）

同一台 macOS，生成 10 秒 1920×1080 测试片，64 段均截取前 9.375 秒。每段按 30 fps 向下取整，视频总长 599.4667 秒；AAC 填充后 MP4 容器时长约 599.53–599.55 秒。旧实现仅解除上限用于基线，保留 `BufferTarget` 与同时加载全部片段；新实现为逐段加载与 OPFS 写出。没有请求外部生成服务。

| 浏览器 | 版本 | 耗时 | 文件字节 | 可观察内存/输出 |
| --- | --- | --- | --- | --- |
| Chrome 152 | 旧内存基线 | 88.740 秒 | 88,678,201 | 主线程 JS 堆采样峰值 79,240,852 字节 |
| Chrome 152 | 流式 | 89.824 秒 | 88,678,209 | 主线程 JS 堆采样峰值 71,355,001 字节；86 次写盘，最大块 1,048,576 字节 |
| Safari 27.0.1 | 旧内存基线 | 285.794 秒 | 111,988,817 | 不提供 JS 堆测量 API |
| Safari 27.0.1 | 流式 | 265.190 秒 | 111,988,825 | 108 次写盘，最大块 1,048,576 字节；不提供 JS 堆测量 API |

主线程 JS 堆不包含 Worker、原生解码器、GPU 与 Blob 后备存储，不能用这些数字宣称整浏览器峰值内存下降；Safari 的测量字段为 0 表示不可用，并非零占用。结构上同时驻留的输入从 64 段缩到当前一段，但单段音频仍需完整 `decodeAudioData`，无 OPFS 的 ZIP 回退仍累计 Blob。

两种浏览器均实际下载流式成片，`ffprobe` 确认 H.264、1920×1080、AAC、48 kHz 双声道；分别在 0、300、598 秒处抽取 0.5 秒解码均通过（未做全片解码）。取消等待解码、磁盘写入背压、写盘失败清理、ZIP 原片内容/顺序与无 OPFS 回退有自动化覆盖。低端设备、iOS 与真实上游长片仍未覆盖；本次不执行生产切换。
