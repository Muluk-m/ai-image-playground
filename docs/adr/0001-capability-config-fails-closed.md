# 能力配置损坏时拒绝启动，而不是降级运行

能力（capability）一律 deny by default，配置文件**不存在**是合法状态（开源自部署本来就没有）并回落到各能力的默认值；但配置文件**存在却损坏或不合 schema** 时，服务拒绝启动。

这么定是因为能力有两类：`operator:console` 这种**授予型**关掉等于功能消失，是安全的；`accounts:login` 这种**门禁型**关掉会停止要求匿名访客先登录。任务归属已独立为行级事实：带 `user_id` 的任务不会因登录能力关闭而公开。但配置损坏若统一回落，经营部署仍会静默开放登录门禁，并关闭依赖登录的计费等能力，实际部署形态与运营者配置不再一致。一个起不来的经营站，远好过一个悄悄改变访问边界和功能集合的经营站。

## Considered Options

- **统一回落默认值，不区分缺失与损坏。** 最简单，但就是上面那个 fail-open。
- **注册表逐个 key 标注回落方向。** 可行，但把「这个 key 该往哪倒」变成每次新增能力都要重新判断的题目，而人会判断错。
- **区分「不存在」与「损坏」。** 采纳。默认方向不需要逐点判断——语义上永远 deny，配置损坏则根本不进入求值。

## Consequences

求值函数本身仍然是全函数、不抛异常：拒绝启动发生在配置加载阶段，不在求值阶段。这跟「服务间令牌在认证开启时缺失即拒绝启动」是同一条纪律，不引入新概念。

代价是经营站的配置文件写坏会导致服务不可用而非降级可用。这是刻意选择的方向。
