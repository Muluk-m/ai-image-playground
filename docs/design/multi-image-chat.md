## 改造前后

| 用户场景 | 当前行为 / 缺口 | 完成后的行为 |
| --- | --- | --- |
| 拖入 100 张本地图片 | 总引用上限 50、内联上限 8；不保证先独立上传 | 有界上传原件，聊天消息仅携带稳定引用；全部 ready 或明确移除失败项后发送 |
| 同一轮多次看图 | 视觉工具结果累积，主要依赖通用上下文治理 | 本步需要的视觉工作集 + token 预算 + 最终 HTTP body 字节硬闸 |
| 为 100 张图统一编辑 | 单份生成草稿对应单任务，`n` 是同一输入的产物数 | 一份批次计划，逐项固定输入与提示词，一次确认，逐项创建现有生成任务 |
| 逐图检查并汇总 | 无独立、持久且有计费归属的分析批次 | 每个必要分析单元可追踪，结论有图片出处，汇总明确已覆盖/失败/未知范围 |
| 中断、刷新与暂停 | 后台生成可继续，缺少稳定批次和派发暂停 | 按批次恢复进度；暂停后已派发的继续，未派发的等待恢复 |
| 历史附件与生成产物 | 有媒体基础设施，未覆盖任意聊天附件全生命周期 | 已发送上传输入随会话保留并计容量；生成产物维持既有保留规则 |

核心链路是「上传一次并保存引用 → 按任务读取视觉证据 → 每项可靠执行 → 汇总有出处的结果」。替换浏览器 JSON 中的 base64 只解决第一段；上游仍可能要求 base64，必须同时解决出站体积、视觉上下文和执行状态。

## 问题与现状

应分别治理浏览器上传、运行期内存、模型请求字节和视觉 token；base64 是传输表示，本身不等于全部作为文字 token 计费。只有存储引用、没有出站预算，仍可能在发送给模型时展开成巨大请求。

现有代码已经具备以下基础，本方案围绕这些模块扩展：

- 发话快照固定参考图和画布身份；云画布已有绑定的图片可转换成 `mediaId`。
- 图片总引用、内联引用和随首轮直接看的媒体引用数量分别受控；大量媒体引用默认只给清单，模型通过 `viewImage` 读取。
- 图片与遮罩归档不直接存入消息文本；跨轮 `replayed()` 恢复纯文本消息，旧图仍可按身份重新读取。**不是每次新发话都自动把全部历史图片重新塞回模型。**
- 同一轮 `viewImage` 和插话会产生新的视觉块；当前主要通过通用上下文压缩治理，尚未找到独立视觉工作集与总出站字节预算。
- 现有视觉 token 估算会按可识别的图片尺寸修正，不是完全忽略图片。入站 HTTP body 上限不等于出站模型预算。
- 媒体服务已有上传预留、二进制 PUT、完成确认、摘要去重、原图和预览；上传接口不依赖项目 ID，但目前依赖登录及 `accounts:sync`。
- 当前前端发话准备仍依赖云画布同步查绑定，不能保证任意聊天附件、独立会话及遮罩都变成媒体引用。
- 遮罩引用在新基线还携带 `editAction` 和编号 `regions`；原图、遮罩及编辑语义必须作为同一份不可变输入保留，不能为了缩图破坏坐标或像素绑定。
- 带遮罩图请求局部细节时可能返回四块视觉证据（原图、定位图、原色选区裁片、额外局部细节）；预算必须计算实际块，不能按一张参考图或固定三块估算。历史超出有效选区作用域时，mask、regions、editAction 一起退出活动编辑意图。
- 已有 `chat` / `canvas` 两种体验。chat 使用对话产物卡，不能默认所有批量结果自动落画布；产物归属跟随发起时的体验。
- 已有后台生成、执行租约、收件箱、唤醒、草稿确认和按快照重试；不从零建设通用任务队列。

现场核查只证明源码行为，不代表已复现用户具体失败请求或验证了生产吞吐。

## 领域边界与既有约束

- 「素材」已经专指同一主体的一组视角图。一次发话附上的任意图片集合不是新的素材，不自动进入素材库。
- 「后台任务」现有含义是生图或生视频，不调用对话模型。第二阶段若增加独立视觉分析执行，必须明确新的执行语义，不能静默改变既有后台任务含义。
- 「停止对话」与停止尚未派发的批量工作不是同一操作；既有后台任务生命周期保持可区分。
- 遵循 [ADR 0012](../adr/0012-agent-background-jobs-and-postgres-inbox.md)：继续 pi 基础 Agent、Postgres/worker 和自有事件协议，已有状态与幂等继续复用。
- 遵循 [ADR 0011](../adr/0011-cloud-storage-limited-to-assets.md)：不借本次改造扩大生成产出的云端长期保存承诺。用户上传的会话输入按已确认 Q5 保留，详见 [ADR 0013](../adr/0013-conversation-input-media-retention.md)。
- 遵循 [ADR 0008](../adr/0008-durable-project-media.md)：使用稳定媒体身份、不可变已确认原件和所有引用的联合回收判据；已有回收设计不能被误写成所有实现均已完成。

## 第一阶段技术设计

### 1. 附件上传与发话解耦

从 `apps/web/src/features/canvas/lib/projectMedia.ts` 抽取不依赖画布的媒体上传客户端，画布同步和会话附件都调用它。复用 `/api/media/uploads`、签名 PUT 和 `/api/media/:id/complete`；不建立第二套对象存储、容量账本或账号身份。

附件准备只处理发话快照固定的像素和编辑信息，不在异步上传后重新读取当前画布。登录用户具有现有媒体上传能力时，普通文件、素材视角、批注合成和遮罩编辑都走同一准备流程；`chat` 体验不再依赖 cloud workspace。未配置必要能力时明确提示，不能静默回落成 100 张内联原件。纯静态 BYOK 生成与匿名生成权限均不在此次扩展范围内。

上传状态与是否发送分开：

```text
本地附件 → 排队 → 上传中 → 校验中 → 就绪
                   ↓          ↓
                 失败 ←───────┘
                   └─ 用户重试 → 复用已确认媒体或恢复上传

全部就绪 → 用户发送 → 服务端受理并建立会话引用
有失败项 → 用户重试或明确移除 → 重新确认发送范围
```

执行有界上传队列，不同时解码/哈希 100 张原图。现有完成处理有单处理门，因此确认请求必须限并发；忙响应使用有界等待，上传阶段可重试与付费生成重试分开。摘要去重命中只复用已确认、属于当前用户的媒体。仅成功 PUT 不算上传完成，只有服务端校验并发布为 ready 才能发送。

### 2. 协议与不可变输入

继续沿用 `AgentTurnReference`，先增后缩扩展媒体引用形态；候选字段如下，最终命名以实现类型检查为准：

```ts
interface AgentMediaReference {
  imageId: string
  mediaId: string
  name?: string
  maskMediaId?: string
  editAction?: AgentImageEditAction
  regions?: readonly AgentMarkedRegion[]
}
```

- `mediaId` 指向这次输入的实际像素。批注烧入、裁剪和扩图产生新像素时，必须上传新的媒体内容，不能假装仍是画布旧原件。
- `maskMediaId` 与原图一起检查属主、ready 状态、尺寸、方向与掩码合法性；`regions` 是定位辅助，mask 仍决定权威编辑范围。
- 一个引用的归档与校验使用整组原图、mask、动作、区域。原件不为适应对话预算而降质；模型看到的预览是派生视觉表示，不改变编辑身份或旧 selection ID 的像素含义。
- 会话媒体认领需同时涵盖原图与 mask。所有引用校验通过后才受理整条消息；不能留下部分已受理的图片范围。
- 旧 inline 协议保留受限兼容，服务端继续能读取既有归档。不把客户端升级与旧历史大规模迁移绑在同一发布上。
- 100 张是逻辑参考图数量，不是媒体对象数量或视觉块数量；一图加 mask 会占多个对象，一次看图还可能产生多个证据块。

### 3. 生命周期与回收

已发送输入由会话引用保护，并使用已有统一用户媒体容量。未发送已确认上传保留短期暂存归属，过期后只有在没有会话、素材、项目或其他有效引用时才能回收。已被其他用途引用的去重对象不因本次附件撤回而删除。

媒体发布、会话引用认领与回收之间需有互斥的状态转换或同一媒体行锁，防止清理器检查“无引用”后、消息刚引用却被删除。删除会话只解除自己的引用；回收再次检查所有归属后才删原件、mask 和派生预览，并只在确实完成回收后释放实际容量。

暂存用显式附件租约记录（候选新表 `agent_attachment_leases`），记录 user、media、expiresAt 和发送请求标识。创建/续租仍按原有能力鉴权，去重命中也要登记本次租约；消息受理事务中先建立会话引用再解除本次租约。浏览器关闭后租约到期即可进入候选回收；任务与会话引用继续保护使用中的输入。只清理本次新流程标记为可回收的对象，不因旧媒体引用生产者尚未齐全就扫描删除全部“无引用”历史对象。

对象删除采用 tombstone 和可重试清理：事务内锁定媒体、再次检查引用/有效租约并标记 deleting，后续认领必须拒绝该状态；事务外删除对象，成功后事务确认释放容量。删除中进程崩溃可重复删除同一 key，不能先释放容量再让对象永久遗留。相同摘要的并发上传遇到 deleting 对象应等待或新建受配额保护的对象，不能把旧对象重新认领成 ready。

这部分是第一阶段的完成条件，不能因现有表里有 `media_references` 就宣称未发送附件已经具备回收。旧 inline 历史保持现有读取路径，无法读取的历史图片明确提示，不编造描述。

### 4. 视觉输入工作集与预算

引入单一视觉输入准备模块，让首轮、插话、`viewImage`、`fetchImage`、`fetchListingImages`、结果复核经过同一策略。每份视觉证据带来源引用、表示类型、尺寸与字节量，原图存储与模型视图分开。当前 `fetchImage` 和 `fetchListingImages` 直接调用 `referenceEvidence` 返回图片，同样必须改接准备器；任何新增返回 image block 的工具都不能绕开它。

优先保留本步必需图片、正在编辑的选区证据和联合比较依赖；已用完的工具图片可从后续模型请求中移除像素，保留身份与已经真实获得的文字结论。仅有 `[image]` 占位符不能算已经理解图片。无法通过少量证据维持完整任务语义时，只有第二阶段分析能力已启用才可转入持久分项分析；第一阶段返回限制和可选操作，不静默漏图。跨轮现有纯文字 replay 保持不变。

治理面分四层：

| 层 | 测量对象 | 约束方式 |
| --- | --- | --- |
| 上传 | 单原件、mask、总用户占用 | 现有容量预留与完成确认；单图格式/像素检查 |
| 运行期 | 同时解码图片与缓冲区 | 有界并发、按图读取、派生结果复用，不集中解码全批 |
| 模型内容 | 实际视觉块、预估视觉 token、文字与工具开销 | 复用 token guard；新增视觉表示选择与工作集淘汰 |
| 模型出站 | 供应商适配后的最终请求体字节 | 发送前硬闸，不能以文件原始字节数或 token 数替代 |

准备阶段先按编码大小做保守预估，减少在末端构造巨大对象；HTTP 出站边界再检查实际序列化结果。原始 N 字节的 base64 长度为 `4 × ceil(N / 3)`，但最终还含协议包装、文字及工具 schema，不能据此替代最终计量。最终 JSON 使用 UTF-8 字节数，不能用 JavaScript 字符串 `.length`。

已核验 lock 固定的 [pi-ai 0.85.1](https://registry.npmjs.org/@earendil-works/pi-ai/0.85.1) 与 [OpenAI SDK 6.40.0](https://registry.npmjs.org/openai/6.40.0)：pi 的 `fetch` 选项会传至 SDK，SDK 先序列化 JSON，再调用注入的 fetch。现有 `model.ts:84–89` 已有 fetch 注入，因此在此增加共享 body guard；`onPayload` 可用于提前估算，但不是最终字节边界。摘要经 `compaction-summary.ts` → `chatCompletion.ts` 独立发送，在该路径已经生成的 body 字符串上调用同一 guard。新独立分析执行器也必须使用同一适配层。

body guard 超限不调用底层 fetch。SDK 会把异常包装为连接错误，pi 又转成错误终帧，因此每次 logical call 用独立闭包记录本地拒绝原因和字节数，在消费终帧时映射为本地预算错误；不能只靠外层 `instanceof` 或错误文本。继续显式 `maxRetries: 0`；本地预算拒绝不计上游 attempt，不触发付费重试。请求表示若从 JSON 字符串变为 Request/stream，必须实现有界测量后才允许该适配器启用，不能静默绕过闸门。

当前 `usage-ledger.ts:43–67` 在真实 fetch 之前 begin 调用就增加 `upstreamInvocationCount`，因此实施必须拆分“建立逻辑调用”和“实际 HTTP 派发”两个事件，把实际计数移到通过 guard 后的派发边界。仅添加拒绝闭包不够；本地拒绝不能变成一次 usage 未知的上游调用并导致全额结算。其他已派发调用仍保留真实用量，整轮最终结算继续遵守既有轮终态规则。

预算满足 `bodyBytes ≤ min(应用硬限额, 已核实网关限额, 已核实供应商限额)`，同时满足当前模型 token 安全预算。未核实的上游值不能猜成无限；启用前为当前路由给出保守配置，并用实际序列化和 mock transport 验证。运行期还限制正在解码的像素总量与缓冲区，防止最终硬闸前就耗尽内存。

超限处理顺序：选择合适预览/局部 → 释放本步不需要的历史视觉块 → 使用当前已启用且语义等价的分批读取能力 → 仍不满足则返回结构化原因与可选操作。第一阶段只支持已有视觉读取与工作集调整，持久分项分析及批次派发由第二阶段能力门控；100 张可上传不等于第一阶段已能自动完成 100 项执行。压缩失败不能回退无界原图再照发。Q7 保护必要细节和完整范围，预览方案必须和原图编辑执行分开。

摘要沿用当前文字 transcript 路径，同时保留有出处的分析结论、图片身份和待处理范围。摘要请求自身继续受 token 与字节预算约束。

### 5. 配置与兼容发布

业务阈值由既有 `operator-config` 单一来源解析，前端只读取服务端求值后的能力/配额，不写进 runtime-config。初步需要区分参考图数量、单次模型请求字节、视觉输入预算、上传/确认并发及未发送附件暂存期限；不把所有限制合并成一个“最多几张图”。100 张是已确认验收目标，其余默认值在实测当前通道上限与资源余量后确定。

发布先扩服务端引用协议和回收保护，再启用新客户端上传；旧客户端及旧 inline 历史保持可读。服务端能力未就绪时前端不能先放宽到 100 张。只读/观测阶段先统计现有请求大小分布，再打开硬闸和新准备路径；回滚关闭新入口而保留新引用的读取支持，不删除已上传数据。

## 第二阶段技术设计

### 6. 批次计划与完整覆盖

新增批次作为用户确认、进度、暂停和汇总的稳定归属，不能把它等同于一轮对话或一次模型请求。复用现有生成任务执行，不把 `n` 上限改成 100。每个独立目标默认一项；该项确实需要多份产物时，仍使用现有单任务的 `n` 和结算规则，不承诺单任务部分成功按张结算。

三种执行计划使用同一份范围清单：

| 指令类型 | 计划 | 完整性判据 |
| --- | --- | --- |
| 统一改图 | 无需先看全部图片即可逐项固定规则、原件和 mask；必要时先分析再拟稿 | 每张目标图都有确认计划和明确终态/阻塞状态 |
| 逐图检查 | 分项视觉分析，保存结构化结论和证据引用，再做汇总 | 每张应检查的图都有实际读取证据和结论；失败/未知不得算已检查 |
| 跨图比较 | 同次请求保留比较必需的联合证据，或按可证明适用的任务结构分解 | 仅在不损失目标所需关系时分解；不能把逐图文字摘要当作任何比较的等价替代 |

例如逐图提取确定字段后排序可按字段聚合；要求所有图片之间精细视觉差异时，摘要分组不保证等价。后者若无法在预算内提供必要证据，给出可操作选择并等待用户，不能擅自变成近似比较。100 张验收不承诺所有精细联合比较都能塞进一次模型调用。

先分析再生成的任务有两个明确阶段：先展示分析预估并启动分析；分析完成得到真实逐项提示词后，再展示并确认最终生成计划。不能让用户确认尚未生成的逐项提示词。纯统一编辑则直接生成整批草稿，一次确认即可。

确认界面展示规则、总项数、输入缩略图、可展开的逐项提示词、模型/参数和预计总消耗。确认固定 `revision + planHash`；重复确认同版只返回同一个批次，过期页面不能确认另一版。新图片、编辑像素变化、规则或提示词变化产生新计划版本，重新确认。已派发版本保持不可变，新增范围不混入旧授权。

### 7. 持久数据与模块边界

以下是拟新增的结构与字段，属于实施规格，不代表已有表：

| 结构 | 核心字段与约束 |
| --- | --- |
| `agent_batches` | id、userId、conversationId、originTurnId、experience/project 快照、revision、planHash、instruction、controlState、dispatchEpoch、pauseReason、createdAt；用户+确认命令唯一 |
| `agent_batch_items` | id、batchId、ordinal、kind（generation/analysis/aggregate）、不可变 input refs/prompt/params、依赖项、executionState、currentAttemptId、result/error；同批 ordinal 唯一 |
| `agent_batch_attempts` | itemId、attemptNo、commandId、taskId、lease/fence、dispatchState、upstreamRequestId、价格/预算快照、时间；item+attemptNo 和 commandId 唯一 |
| `agent_analysis_calls` | analysis task/attempt、logical call/HTTP attempt、dispatch intent、upstream ID、usage 状态与计价事实；独立分析计费事实的唯一来源，不随会话删除级联 |
| `agent_analysis_results` | itemId/attemptId、结构化 findings、evidence refs（media/region/representation）、coverage、输出版本；无 base64，保留同一执行的出处 |
| `agent_attachment_leases` | userId、mediaId、发送请求标识、expiresAt；提供暂存归属，不替代会话引用或容量账本 |

批次与处理项存逻辑身份；任务仍是实际执行和计费单位。attempt 表记录应用执行尝试，与每次真实 HTTP 派发分别留痕，不能用一个 attempt 掩盖多次上游请求。范围上限为 100 张输入，分析/生成/汇总的处理项数可能不同，不把这两种计数混用。

读写边界：

- 附件客户端负责上传状态和引用准备；BFF 媒体服务负责校验、容量与引用，不知道模型提示词。
- 视觉输入准备器负责从指定证据构造有预算的模型视图，不修改原件与已确认提示词。
- 批次服务负责版本确认、授权快照、依赖、暂停和幂等；调度器只从可运行项创建实际任务。
- 生成项调用现有任务提交、预扣、worker、归档和 Agent 结果登记；以 batch/item 标识关联既有任务。
- 分析项使用专属分析执行器及持久用量归属，不把新模型调用伪装成普通生图，也不追加到已经结算的原对话轮。
- 前端按持久事件和分页状态渲染；chat 输出对话产物卡，canvas 输出遵循发起时项目及画布归属，不能恢复时改投当前打开画布。

### 8. 分析执行与计费隔离

按 [ADR 0014](../adr/0014-batch-analysis-execution-and-accounting.md)，采用显式新任务类别 `analysis`，复用既有 Postgres、worker 进程与计费 hooks，增加专属 claim/lease/recovery/finalize 路径。现有 `queue | chat` 的数据库约束与共享类型先扩展；通用图片/视频 claim 必须显式白名单 `queue`，不能只依赖 scheduler 查询过滤。`chat` 保持原轮占用含义，不把它改成 queued 来偷渡异步分析。

分析执行器输入仅为该处理项需要的指令、不可变引用与依赖结论，输出受 schema 约束的 findings/coverage/evidence。每个执行项对应一次有界模型调用；运行中还需补看时，新增项进入新计划版本，展示新增费用后由用户重新确认，不能在冻结的 planHash 下临时追加付费项。初版不实现预算内自由扩张的动态分析图。整批汇总如需要另一次模型调用，也作为明确分析项计量；确定性聚合优先由代码完成。

需要同时修改任务查询、claim、maintenance、取消路由、成本分类和 Admin 展示。当前某些成本归集把非 chat、非 video 算成 image，必须显式新增 analysis 类别。现有 `finishTask` 会触发生成档案与产物发布，不能直接套给分析；提取公共状态/结算事务，分析终结器只发布分析结果与批次事件。

现有 `agent_model_calls` 绑定 conversation/turn，且会话删除会级联清理，不适合作独立分析的唯一计费事实。新增 `agent_analysis_calls` 按 analysis task/attempt 归属保存逻辑调用和真实 HTTP 派发、用量状态，task 外键禁止在未结算时被删除，conversation 关联允许置空。公共指标查询统一聚合这两种调用事实，但分析调用不再写进原轮用户用量账本，也不复制一份可重复结算的记录。每次调用只有一个用户计费归属；原轮 ID 仅作溯源，平台承担的 compaction/web_search 规则不被借用。图片生成沿用现有生成定价，普通对话沿用按轮计费。

已核对 `private.lock` 钉住的 overlay `cf17a054208ad9a6e28f4daf33528e72587cad8a` 的 [预扣 hooks](https://github.com/Muluk-m/ai-image-playground-private/blob/cf17a054208ad9a6e28f4daf33528e72587cad8a/apps/bff/billing/service.ts#L186-L266) 与 [结算规则](https://github.com/Muluk-m/ai-image-playground-private/blob/cf17a054208ad9a6e28f4daf33528e72587cad8a/apps/bff/billing/settlement.ts#L45-L94)（未运行该组合测试）：预扣/结算 hooks 可复用，但 `reserveChatTask` 强绑定 turnId/Agent 租约，不能直接用于分析。提取 token 计价与结算公共原语，分析沿用当前对话计费能力及 `billing:chat-free` 豁免，不因改为后台执行让原本免费的对话分析突然收费；生成费用仍独立。展示区分预计用量、预计实扣与实际费用。

### 9. 状态机、暂停和幂等

批次分开保存控制状态与派生进度，避免 paused 被误认作所有任务都停止：

```text
控制：draft → awaiting_confirmation → running ↔ paused
                                        └→ closed
进度：待处理 / 在途 / 成功 / 明确失败 / 结果未知 / 依赖阻塞

处理项：pending → ready → dispatching → running → succeeded
                    │          │           ├→ failed
                    │          └───────────┴→ unknown
                    └→ blocked（依赖未满足或批次公共阻塞）
```

只在所有项都有确定结局、没有待派发/在途/unknown 时关闭；关闭结果区分全部成功、部分失败、全部失败。用户显式放弃剩余项记为 skipped，不能算成功。unknown 是仍待核实的状态，批次不能宣称全部结束或给出完整覆盖结论。用户重试产生新 attempt，原失败与旧账单保持不变。

派发与暂停的线性化点在同一数据库批次行锁：

1. 调度器锁批次/处理项，校验 running、epoch、确认版本、依赖、能力、预算；同一事务内为该项创建任务、预扣、写幂等键及 batch/item 关联。
2. 事务提交代表该项已派发。暂停也锁同一批次行并更新 controlState/epoch，因此暂停成功响应后不会新提交旧 epoch 的项；暂停前已提交、即使还排在生成队列里的任务仍按已派发项继续。
3. 暂停响应返回当前在途/已派发数量，UI 清楚展示「已提交项继续」。调度器不能先选满 100 项在事务外继续提交，派发窗口受全局/用户并发配额约束。
4. 恢复重新校验权限、价格、输入可用性和依赖，只派发从未提交的项。已绑定 taskId 的项跟随其既有状态，不能因批次租约过期再创建任务。

task 创建与预扣、关联必须同事务；提交后但事件发送前崩溃，从任务关联恢复。worker HTTP 派发前持久记录 dispatch intent；发送与上游接收无法原子化，网络超时/重启留下不确定结果时标 unknown，优先凭上游 request/idempotency ID 查询。支持的上游才可按其幂等协议安全恢复；不支持查询时等待人工核实，不自动重发。租约 fence 防止旧 worker 回写覆盖新状态，**不能**宣称本地租约等于上游 exactly-once。

用户停止对话仅终止当前回复；批次卡独立暂停。删除会话复用既有取消语义，并原子阻止该会话的新批次派发；已被上游接受的工作仍需收尾记账。删除只解除展示关联：batch 的 conversation 外键使用 nullable/SET NULL，item/attempt、分析调用事实、报价快照、HTTP 派发及未结算证据由任务持有，不能 CASCADE 随会话删除。结算关闭后按既有账单审计与业务数据清理规则处理，内容快照只保留在途执行必要部分，不把所有已删会话文字永久留作日志。在途处理所需媒体引用到最终收尾才解除，不因会话删除造成悬空输入；保留期限不因此扩大为永久生成产物存储。

### 10. 费用、失败与恢复

整批确认是确认执行范围和预计消耗，实际预扣仍逐项执行，避免同时整批预扣又逐项预扣。确认计划固定模型、输入、参数及报价版本；开始派发前校验价格事实，涨价或所需预扣超出已展示预算时暂停并展示更新后的未执行部分，不静默扩大费用。已预扣项按原价格事实结算；用户重试使用当前价格，按钮明确展示。

当前 hooks 将 completed+已知 usage 按实际折算（最高不超过预扣），completed+usage 缺失按预扣额结算，failed/cancelled 释放预扣；套餐跨期退款仍遵守既有规则。**本方案不承诺缺失 usage 也能按精确实际用量结算，不用批次完成百分比代替各任务结算。** 0 usage 必须与 unknown usage 分开，不能把真实零用量转 null 后全额结算。

为支持重启，分析 task/attempt 持久保存预扣时输入估算、输出预留、基础单价、输出/缓存倍率、豁免结果和价格版本。取价与预扣需要同一价格版本约束，不能在两个查询间价格变化却生成拼接快照，也不能恢复时只拿 model 再读现价。这些是新增要求，不宣称当前闭包计价已经满足。

unknown 不直接当普通失败重试或释放后重发。当前 `upstream_result_unknown` 最终可能落 failed 并触发释放预扣，所以只给 batch item 增加 unknown 不够：新增 task 非终态 `reconciling`，映射 item unknown，hold 保持 reserved，不调用终态 finalize。该分支初期只由新批次任务使用，既有历史不改写。maintenance、用户取消、删除会话、租约回收都不得把 reconciling 当 failed/cancelled 自动释放或重排；取消仅停止后续派发，核查责任仍存在。查询确认成功后落 completed 并按已知 usage 或既有缺失 usage 规则结算；确认未产生结果后落 failed 并释放。无法查询时保留待核查状态，提供人工裁决入口，记录依据、幂等 settlement 命令与操作者，不能以超时自动判失败。相关数据库 status 约束、状态查询、Admin 展示与回滚兼容一起扩展。

自动生成重试保持关闭；本地预算拒绝没有上游调用，释放对应未消费预扣。单项明确失败不停止其他无依赖项；依赖失败则下游 blocked，并在汇总列出缺项。余额不足、鉴权失效、整条通道不可用通过结构化错误暂停相关批次的后续派发，避免把同一个公共故障扩散成 100 次失败。

批次费用仅聚合任务账单 ID，不另外扣费。页内分别展示分析、生成、普通对话/结果复核费用；同一模型调用不可同时计入分析任务和原对话轮。唤醒按 batchId 聚合事件，复用现有自动唤醒预算，不为 100 项各起收费复核；确定性进度更新不调用模型，自动复核如发生仍显式按现有轮计费。

### 11. 接口与交互契约

路由名是候选，实施时对齐已有 Agent router；所有接口复用现有会话属主鉴权、能力求值和请求防护，不根据“免费/付费”字符串放行。

| 接口 | 行为与关键约束 |
| --- | --- |
| 既有媒体上传/complete | 增加附件暂存租约；使用原二进制上传和容量校验 |
| 既有 turn submit | 扩展 media mask/action/regions，原子认领全部引用；requestId 幂等发送 |
| `POST /api/agent/batches` | 建立可编辑草稿与覆盖范围，不能创建付费生成任务 |
| `POST /api/agent/batches/:id/confirm` | 携带 revision/planHash/commandId，原子冻结计划与报价；重复请求返回同批，旧版本返回冲突 |
| `GET /api/agent/batches/:id` | 汇总、控制状态、费用、覆盖范围及事件游标 |
| `GET /api/agent/batches/:id/items` | 按稳定 ordinal 游标分页，不把全部大结果塞进一条会话消息 |
| `POST /api/agent/batches/:id/pause`、`resume` | 幂等，带预期版本；暂停回报已派发数，恢复重新检查能力及预算 |
| `POST /api/agent/batches/:id/retry` | 用户选定明确失败项，返回本次价格；重试命令幂等，unknown 返回需核查，禁止直接重发 |

事件复用现有持久 inbox/事件通道，增加 batch/item 标识和版本；SSE 断连后从游标补读或重新获取汇总，状态在数据库，不能只存在前端 stream。批次卡显示上传进度、计划待确认、执行中、已暂停、需处理及最终明细；失败附件可重试或移除，失败执行项可单选/多选重试。批级重试与逐项重试都引用同一个 attempt 幂等约束。

### 12. 兼容、迁移与回滚

1. 先增加 nullable 引用字段、附件租约及批次表；旧消息按原路径读。新媒体引用解析、所有 owner/ready/mask 校验和回收保护先部署。
2. 先上线出站计量与明确本地错误分类，再开启预算硬闸及前端上传链路；首阶段成功后再开放 100 张入口。
3. `analysis` kind 和 `reconciling` 非终态需要消费者先兼容：数据库 check、类型、旧队列 claim 排除、maintenance/cancel/统计/overlay 同步接缝全部准备好，仍关闭生产者；不能向不认识新 kind/status 的旧 worker 提前写新任务。
4. 批次生产者和分析执行器通过服务端能力逐步开启。收费接缝遵守公开宿主先扩展、overlay 再使用、最后更新 `private.lock` 的顺序；验证 pinned overlay，而非随便一个本地 HEAD。
5. 回滚先关闭新建批次/分析派发；读取新引用、任务状态和计费收尾代码必须保留。已有新 kind 或 reconciling 状态时只回滚到兼容版本，等待/排空后才能收缩，不能删除新字段或把 analysis 交给生图 worker。

生产部署仍遵循 main 合并后的既有 Actions 流程；本文是方案，没有进行发布或生产付费验证。

## 实施拆分与验收

### 实施顺序

| 顺序 | 交付切片 | 必须闭合的用户链路 |
| --- | --- | --- |
| P1.1 | 通用上传、附件租约、mask 媒体协议 | 本地/素材/批注/独立 chat 图片上传并发送，失败不漏图，删除和回收安全 |
| P1.2 | 视觉证据模型与统一准备 | 首轮、插话、viewImage、fetchImage、fetchListingImages、结果复核都保留正确编辑身份，原图不变 |
| P1.3 | 出站字节 guard、预算配置和诊断 | 主模型和摘要精确测量，超限网络调用为零，错误可区分 |
| P1.4 | 100 张入口和历史兼容 | 100 张上传、发送、再次查看及恢复；受控内存与无隐式降质 |
| P2.1 | 批次计划、一次确认、逐项生成 | 100 个不同输入可追踪生成，幂等确认，无重复预扣 |
| P2.2 | 显式分析 task 和持久计费 | 分项读取、结果出处、独立计费、重启恢复与完整覆盖 |
| P2.3 | 暂停/恢复、失败/unknown、事件聚合 | 在途继续、后续停止、明确失败重试、unknown 不重发 |
| P2.4 | 联合任务规划与最终汇总 | 按目标决定读取方式，完整性可证明或明确要求用户选择 |

P1 是可独立交付的可靠性改造，不能宣称已经支持全部批量执行。P2.1 的暂停/fence/幂等底座需同步具备，P2.3 扩充恢复 UI 与全场景验证；不能先放出不可暂停的 100 项自动派发。每片实施时单独测试、review；整体规格已由用户调用 to-spec 发布为 #938，尚未拆 tickets 或实施。

### 验收矩阵

| 场景 | 通过条件 |
| --- | --- |
| 100 张不同图，含大尺寸、重复内容 | 上传有界；去重按用户隔离；最终消息只有小型引用；每个逻辑输入保留顺序及身份 |
| 99 张 ready、1 张失败 | 不能偷偷发送 99 张；只重试失败项或用户明确移除后发送 |
| 100 张带遮罩/区域的图 | 原件与 mask 成对校验；算实际证据块；不能靠缩原件破坏选区 |
| PNG/JPEG/WebP 以外输入、超大像素、预览转换失败 | 支持范围与已有媒体接口一致，明确规范化或拒绝；不回退无界原图直发 |
| 首轮、连续 viewImage、fetchImage、fetchListingImages、插话、唤醒、摘要 | 每条出站路径受预算；旧视觉退出后保留出处和真实结论，必要联合证据不丢 |
| 中文/emoji/base64 与 SDK 包装错误 | UTF-8 计量准确；本地超限底层 fetch 和实际派发计数均为 0；保留本地诊断，不虚增未知 usage 或触发其全额结算 |
| 重复发送/确认，刷新后再次确认 | 一条消息/一份批次及每项任务不重复；无重复预扣 |
| 暂停与并发派发竞态 | 暂停事务后无新项提交；响应展示已派发数；恢复仅处理未派发项 |
| 任务创建后崩溃、请求发出后超时 | 前者从关联恢复，后者 item unknown/task reconciling 且 hold 保留；不会生成第二个上游请求 |
| 1 项明确失败、余额不足、权限失效 | 独立项按规则继续；公共阻塞暂停；依赖失败标缺项，不伪造完成 |
| 实际 usage 为 0 / 缺失，重启后价格变化 | 零与未知分开；持久价格快照；每调用一个计费归属，无重复扣费 |
| chat-free / 非计费部署 / 未登录 | 保持既有能力与豁免，生成权限不扩张；不得因为附件协议绕过门禁 |
| 清理与发送/去重并发、删除会话时任务在途 | 被认领或仍在用的媒体不删；孤儿最终回收且容量只释放一次；删除后仍有任务/调用/报价事实可结算 |
| SSE 断联与旧客户端、旧 inline 会话 | 从持久状态补进度，历史可读，新生产者关闭时旧用户链路继续可用 |
| 精细联合比较超限 | 明确无法保证目标的原因及可选操作，不把近似汇总声称为完整比较 |

验证分三层：纯单元覆盖表示/预算与状态判定；PostgreSQL 集成覆盖并发、幂等、引用/预扣/任务原子性与迁移回滚；浏览器覆盖上传失败恢复、100 张进度、确认和暂停。上游调用使用可记录真实序列化请求的 mock transport，注入限额、超时和不确定回执，不用付费生成做压力测试。收费版需 pinned overlay 组合测试及 overlay 缺席验证；按仓库规范跑指定 app 测试/CI，全量验证遵守远端资源约定。

上线验收需真实登录、上传、历史读取与线上版本，选择受控范围验证实际 provider 兼容；生产付费调用如需额外授权再单独界定。mock 通过不能证明供应商吞吐或 100 项付费链路已在生产跑通。

### 可观测性和上线门槛

在现有 model call/任务诊断上增加：logical refs / 实际视觉块数、预估视觉 token、源图/派生图字节、最终 body bytes、budget/预算拒绝层、实际 HTTP 派发数、batch/item/attempt ID、报价版本、费用归属、覆盖数、unknown 数、暂停原因、上传/确认排队时间和内存峰值。只记录计量与 ID，复用现有脱敏失败结构，不记录 base64、签名 URL 查询参数或鉴权信息。

实施前需以当前部署测出并登记：各通道有效出站体积限制、单图像素/解码内存限制、上传和确认并发、用户批次派发窗口、视觉工作集预算、附件租约时长。仅 100 张是已确认产品验收目标，其他数值不得伪装成供应商通用保证。硬闸的准入条件是支持路径全部计量、未知表示不绕过、拒绝时零派发；批次准入条件是并发暂停/幂等/计费/恢复集成用例通过。

## 调研结论如何落到本方案

[开源源码调研](../research/multi-image-chat-oss-2026-10-01.md)覆盖 13 个项目，包括 Open WebUI、LibreChat、Cherry Studio、Jan、Chatbox，也包含 AionUi、CoPaw、AstrBot、SillyTavern、ChatALL、AIChat、Page Assist、big-AGI。固定提交证据支持的是各项目各层实现，不证明它们全部具备本方案的 100 项可靠批处理。

共性可以借鉴：附件对象化、稳定身份与预览、按需转换为上游协议。差异必须保留：部分项目最终仍展开为 base64；provider 文件 ID、URL、inline 支持及保留范围不同，不能把某家的 ID 直接发给另一家。跨供应商通用的是应用层媒体身份和预算边界，最终传输由适配器决定。本方案不推断 ChatGPT 等闭源产品内部实现，也不声称仅把 base64 换成 URL 就减少视觉 token。
